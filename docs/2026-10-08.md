## 오늘 새로 쓴 명령

| 명령어 | 의미 |
|---|---|
| `git config` | Git에 사용자 이름과 이메일을 설정한다. |
| `git status` | 파일의 변경 상태를 확인한다. |
| `git add` | 다음 커밋에 포함할 파일을 선택한다. |
| `git commit` | 선택한 파일의 변경 사항을 기록한다. |
| `git push` | 로컬 저장소의 커밋을 GitHub에 업로드한다. |

추가로 사용한 명령어

- `git diff --cached --check` : 스테이징된 변경 사항에서 불필요한 공백 등의 오류를 확인한다.
- `git diff --cached --name-only` : 다음 커밋에 포함될 파일 이름을 확인한다.

## 찾아보고 알게 된 것

### 1. add와 commit과 push는

Git으로 파일을 올릴 때 세 단계를 거치는 이유는 변경 사항을 선택하고, 기록하고, 공유하는 과정을 구분하기 위해서다.

- **add** : 어떤 파일을 기록할지 선택한다.
- **commit** : 선택한 변경 사항을 하나의 버전으로 저장한다.
- **push** : 로컬에 저장한 커밋을 GitHub에 전송한다.

커밋할 때 메시지를 작성하는 이유는 나중에 어떤 작업을 했는지 알아보기 위해서다.

### 2. untracked · tracked · staged는

- **untracked** : Git이 아직 추적하지 않는 새로운 파일이다.
- **tracked** : Git이 이미 관리하고 있는 파일이다. 수정하면 `modified` 상태로 나타난다.
- **staged** : `git add`로 선택되어 다음 커밋에 포함될 준비가 된 상태다.

`git status`에서는 보통 아직 선택하지 않은 변경 사항이 빨간색, 선택한 변경 사항이 초록색으로 표시된다.

### 3. .gitignore의 역할

`.gitignore`는 Git이 추적하지 않아야 할 파일이나 폴더를 지정하는 파일이다.

현재 설정한 내용은 다음과 같다.

```gitignore
.env
.venv/
__pycache__/
```

- `.env` : API 키와 같은 환경변수 정보
- `.venv/` : Python 가상환경
- `__pycache__/` : Python 실행 중 생성되는 캐시 폴더

단, 이미 Git이 추적 중인 파일에는 `.gitignore`만으로 추적 제외가 적용되지 않는다.

## 오늘 실습한 과정

### 1. Git 사용자 정보 설정

```bash
git config --global user.name "YOO JIMIN"
git config --global user.email "GitHub에 등록한 이메일"
```

설정한 정보는 `git config --global user.name`과 `git config --global user.email`로 확인했다.

### 2. 파일 상태 확인

```bash
git status
```

어제 GitHub 저장소를 연결했던 폴더에서 작업했다.

새로운 Python 파일과 Jupyter Notebook이 `Untracked files`에 표시되었고, 기존 노트북 일부는 `modified`로 표시되었다.

### 3. 파일 선택

먼저 `.gitignore` 파일을 별도로 커밋하고 GitHub에 업로드했다.

이후 수업 산출물을 선택했다.

```bash
git add agent_core docs
```

`git status`에서 선택한 파일이 `Changes to be committed`에 표시되는 것을 확인했다.

### 4. 커밋 전 확인

```bash
git diff --cached --check
```

공백 검사에서 문제가 발견되어 파일을 수정한 뒤 다시 `git add`했다.

```bash
git diff --cached --name-only
```

커밋에 포함될 파일 목록을 확인했다.

`.env`와 `.venv`는 목록에 포함되지 않았다.

### 5. 커밋 및 업로드

```bash
git commit -m "Add notebooks and outputs from 10/2 and 10/6"
git push
```

- 커밋 ID : `a2130e4`
- 변경 사항에 포함된 파일 : 17개
- GitHub `main` 브랜치 업로드 성공

`docs/2026-10-07.md`와 `docs/2026-10-08.md`도 함께 업로드했다.

## 막힌 것

### 1. git config 오타

처음에 `git congig`라고 입력해서 다음 오류가 발생했다.

```text
git: 'congig' is not a git command.
```

**해결:** `congig`가 아니라 `config`로 수정했다.

→ 명령어 철자를 정확히 입력해야 한다는 것을 알게 되었다.

### 2. GitHub 로그인 인증

처음 `git push`를 실행했을 때 브라우저 인증 화면이 나타났다.

**해결:** `Sign in with your browser`를 선택하고 GitHub에서 권한을 승인했다.

→ GitHub에 업로드하려면 원격 저장소에 접근할 수 있는 인증이 필요하다.

### 3. LF와 CRLF 경고

`git add` 실행 중 다음 경고가 발생했다.

```text
LF will be replaced by CRLF
```

**알게 된 점:** LF와 CRLF는 줄바꿈 방식의 차이이며, Git이 줄바꿈을 변환할 수 있다는 안내였다.

파일 업로드 자체가 실패했다는 의미는 아니었다.

### 4. trailing whitespace 경고

```text
agent_core/rule_demo.py:1: trailing whitespace.
```

**원인:** `rule_demo.py`의 첫 번째 줄 끝에 불필요한 공백이 있었다.

**해결 방법:**

1. VS Code에서 해당 파일의 공백을 삭제했다.
2. `git add agent_core/rule_demo.py`로 다시 등록했다.
3. `git diff --cached --check`를 재실행했다.
4. 아무것도 출력되지 않는 것을 확인했다.

### 5. API 키가 업로드될까 봐 걱정됨

`.env`에 저장한 API 키가 실수로 GitHub에 올라갈 수 있다는 점을 알게 되었다.

VS Code 전체 검색에서 `AIza`, `API_KEY` 등을 확인했고, `demo-key`라는 실습용 값도 발견했다.

**알게 된 점:** `.env`를 제외하더라도 Python 파일이나 노트북에 직접 작성한 비밀 키까지 자동으로 보호되는 것은 아니다.
