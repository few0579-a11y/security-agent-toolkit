## 5교시 · 어제 명령 복습 · 서버 두 대 켜고 접속 기록 구분해 읽기

### 문제 5-1 · 어제와 같은 명령으로 서버 두 대를 켜고 접속 기록을 구분해 읽기

- (가) 내가 `web-three` 와 `web-four` 를 켠 `docker run` 명령 두 개를 붙여 넣어 주세요.
  - 쓸 내용: 윈도는 `MSYS_NO_PATHCONV=1` 부터, 맥북은 `docker run` 부터 친 그대로 두 줄
  - 답:

```
MSYS_NO_PATHCONV=1 docker run -d --name web-three -p 8082:80 -v "$(pwd)/site-three:/usr/share/nginx/html:ro" nginx:1.28

MSYS_NO_PATHCONV=1 docker run -d --name web-four -p 8083:80 -v "$(pwd)/site-four:/usr/share/nginx/html:ro" nginx:1.28

```

- (나) 🔍 `docker ps` 에서 `web-three` 와 `web-four` 줄의 `PORTS` 값을 각각 적어 주세요.
  - 쓸 내용: 「web-three: … / web-four: …」
  - 답:

web-three: 0.0.0.0:8082->80/tcp, [::]:8082->80/tcp
web-four: 0.0.0.0:8083->80/tcp, [::]:8083->80/tcp

- (다) 🔍 8082 로 세 번, 8083 으로 한 번 접속했을 때 `docker logs web-three` 와 `docker logs web-four` 의 `"GET / HTTP/1.1"` 줄은 각각 몇 개였고, 왜 그렇게 나뉘나요?
  - 쓸 내용: ① web-three 의 줄 수 ② web-four 의 줄 수 ③ 그렇게 나뉘는 이유(어느 포트로 온 요청이 어느 서버에 기록되는지)
  - 답:

`web-three`에서는 `"GET / HTTP/1.1"`이 4개, `web-four`에서는 3개 확인되었다.

두 서버는 서로 다른 컨테이너로 실행되고 있으며, 각각 8082번과 8083번 포트를 사용하기 때문에 접속 요청과 로그가 서버별로 구분되어 기록된다.


- (라) 🔍 `stop` 뒤에 `docker ps` 와 `docker ps -a` 에서 두 서버가 각각 어떻게 보였고, `rm` 뒤에는 어떻게 되었나요?
  - 쓸 내용: 「stop 뒤 ps: … / stop 뒤 ps -a: … / rm 뒤 ps -a: …」
  - 답:
    docker stop으로 두 서버를 종료한 뒤 docker ps에서는 두 서버가 보이지 않았지만, docker ps -a에서는 Exited (0) 상태로 남아 있었다.

이후 docker rm으로 두 컨테이너를 삭제하자 docker ps -a에서도 모두 사라졌다.


- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(서버를 몇 대 어떻게 켰고 기록이 어떻게 남았는지)
  - 답:

    고객용 서버(web-three)와 직원용 서버(web-four)를 각각 8082번과 8083번 포트로 실행하고, 접속 기록이 서버별로 구분되어 남는 것을 확인한 뒤 두 서버를 종료하고 삭제했습니다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답:

같은 Docker 이미지를 사용하더라도 컨테이너마다 이름과 포트를 다르게 설정해 별도의 서버를 실행할 수 있고, 각 서버의 접속 기록도 따로 확인할 수 있다는 것을 알게 되었다.



## 6교시 · 내 이미지 만들기 (Dockerfile)

### 문제 6-1 · Dockerfile 두 줄을 써서 내 이미지 만들기

- (가) 내가 쓴 Dockerfile 두 줄을 붙여 넣어 주세요.
  - 쓸 내용: Dockerfile 두 줄(`FROM` 줄 · `COPY` 줄)
  - 답:

```
FROM nginx:1.28
COPY site-three/index.html /usr/share/nginx/html/index.html
```

- (나) 🔍 `FROM` 과 `COPY` 가 각각 하는 일을 적어 주세요.
  - 쓸 내용: ① FROM 이 하는 일 ② COPY 가 하는 일
  - 답:

      FROM은 새로운 이미지를 만들 때 사용할 기존 이미지(nginx:1.28)를 지정하는 명령어이다.
      COPY는 내 PC의 site-three/index.html 파일을 Docker 이미지 내부의 /usr/share/nginx/html/index.html 경로로 복사하는 명령어이다.

- (다) 🔍 5교시와 달리 `docker run` 에 `-v` 가 없는데도 내 화면이 나오는 이유는 무엇인가요?
  - 쓸 내용: ① 어제 파일이 컨테이너에 닿던 방법 ② 오늘 파일이 서버에 있는 위치와 시점
  - 답:
      
      5교시에는 -v 옵션으로 내 PC의 폴더를 컨테이너에 연결했지만, 6교시에는 docker build 과정에서 HTML 파일을 이미지 내부에 복사했기 때문에 -v 옵션 없이도 내 웹페이지가 나타난다.

- (라) 🔍 `docker build` 출력에서 `[2/2] COPY` 줄과 `naming to` 줄을 붙여 넣고, 각각 무엇을 알려 주는지 적어 주세요.
  - 쓸 내용: ① 두 줄 ② 각 줄이 알려 주는 것
  - 답:

```
[2/2] COPY site-three/index.html /usr/share/nginx/html/index.html

Dockerfile의 두 번째 단계인 COPY가 처리되어 HTML 파일이 이미지 내부에 복사되었음을 알려 준다.


naming to docker.io/library/my-nginx:1

이미지 빌드가 완료되고 생성된 이미지에 my-nginx:1이라는 이름과 태그가 지정되었음을 알려 준다.
```


## 7교시 · 이미지 버전 다루기 · 되돌리기 · 정리 · 올리기

### 문제 7-1 · 파일을 고쳐 보고, 이미지를 다시 만들어 반영하기

- (가) 파일을 고친 직후 새로 고침했을 때 화면에 무엇이 나왔나요?
  - 쓸 내용: 새로 고침했을 때 보인 화면의 큰 제목
  - 답:
      HTML 파일을 site-three v2로 수정하고 새로고침했지만, 화면에는 기존 제목인 site-three가 그대로 나타났다.

- (나) 🔍 파일을 고쳤는데도 화면이 바뀌지 않은 이유와, 바꾸려면 무엇을 해야 하는지 적어 주세요.
  - 쓸 내용: ① 바뀌지 않은 이유(서버가 보는 파일이 어디 있는지) ② 바꾸려면 할 일
  - 답:
      기존 Docker 이미지는 빌드 당시의 HTML 파일을 가지고 있기 때문에 내 PC의 파일을 수정해도 자동으로 반영되지 않는다.

      변경된 내용을 반영하려면 `docker build`로 새 이미지(`my-nginx:2`)를 만들고, 기존 컨테이너를 삭제한 뒤 새 이미지로 컨테이너를 다시 실행해야 한다.

- (다) 🔍 5교시의 `-v` 방식과 6교시의 이미지에 넣는 방식은 파일을 고쳤을 때 반영되는 방법이 어떻게 다른가요?
  - 쓸 내용: ① -v 방식의 반영 방법 ② 이미지에 넣는 방식의 반영 방법
  - 답:
      5교시의 `-v` 방식은 내 PC의 폴더를 컨테이너에 직접 연결하기 때문에 파일을 수정한 뒤 브라우저를 새로고침하면 변경 내용이 반영된다.

      반면 6교시의 `COPY` 방식은 이미지를 빌드할 때 파일을 복사하므로, 파일을 수정한 뒤 이미지를 다시 빌드하고 컨테이너를 교체해야 변경 내용이 반영된다.


### 문제 7-2 · 이전 버전으로 되돌리고 쓰지 않는 이미지 지우기

- (가) 이전 버전으로 되돌린 뒤 `docker ps` 의 `IMAGE` 칸 값과 브라우저에 나온 제목을 적어 주세요.
  - 쓸 내용: 「IMAGE: … / 브라우저 제목: …」
  - 답:
      이전 버전으로 되돌린 뒤 docker ps의 IMAGE 값은 my-nginx:1이었고, 브라우저에는 site-three라는 제목이 나타났다. 따라서 이전 버전으로 정상적으로 복구된 것을 확인했다.

- (나) 🔍 쓰고 있는 `my-nginx:1` 을 `docker rmi` 로 지우려 했을 때 에러 문구의 핵심과, 어떻게 해결했는지 적어 주세요.
  - 쓸 내용: ① 에러 문구의 핵심 ② 지워지지 않은 이유 ③ 해결한 순서
  - 답:
      container ... is using its referenced image라는 오류가 발생했다. 이는 my-site 컨테이너가 my-nginx:1 이미지를 사용 중이어서 삭제할 수 없다는 의미이다.

      따라서 docker rm -f my-site로 컨테이너를 먼저 삭제한 뒤, docker rmi my-nginx:1을 실행하여 이미지를 삭제했다.

- (다) 🔍 이미지에 `:1` · `:2` 같은 태그를 붙여 두면 문제가 생겼을 때 어떤 점이 좋은가요?
  - 쓸 내용: ① 되돌리는 방법 ② 어느 버전이 켜져 있는지 아는 방법
  - 답:
      이미지에 `:1`, `:2`와 같은 태그를 붙이면 버전별로 이미지를 구분할 수 있다. 
      새로운 버전에서 문제가 발생하더라도 이전 버전의 이미지로 컨테이너를 다시 실행하여 빠르게 복구할 수 있다.

- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(되돌린 일과 정리한 일)
  - 답:
      새 버전(v2)에 문제가 발생했다고 가정하여 이전 버전 이미지(my-nginx:1)로 서버를 복구했고, 
      이후 사용하지 않는 컨테이너와 이미지(my-nginx:1, my-nginx:2)를 모두 정리했습니다.

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답:
      Docker 이미지는 버전별로 관리할 수 있어 새로운 버전에 문제가 생기면 이전 이미지로 서버를 복구할 수 있다는 것을 알게 되었다. 
      또한 사용 중인 이미지는 바로 삭제할 수 없으며, 해당 이미지를 사용하는 컨테이너를 먼저 삭제해야 한다는 것도 알게 되었다.


### 문제 7-3 · 오늘 만든 것을 깃허브에 올리기

- (가) `git status` 를 쳤을 때 빨간 목록에 줄이 몇 개였는지, 그 가운데 `.env` · `.venv` 가 있었는지 적어 주세요.
  - 쓸 내용: ① 빨간 목록의 줄 수 ② .env · .venv 가 있었는지
  - 답:
