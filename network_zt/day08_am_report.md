### 문제 2-1 · 알림 A 확인 — 서버 두 대로 열려 있는지 재고, 설정 값 · 비밀번호 · 실행 사용자까지 점검하기

- (가) `docker ps` 의 `PORTS` 열에서 두 서버가 각각 어떻게 나왔는지 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 PORTS 값 ② open-web-8082 의 PORTS 값
  - 답:
      - `closed-web-8081`: `127.0.0.1:8081->80/tcp`로 표시되었으며, 내 PC 내부에서만 접근할 수 있도록 설정되어 있다.
      - `open-web-8082`: `0.0.0.0:8082->80/tcp`로 표시되었으며, 모든 네트워크 주소로 포트가 열려 있어 방화벽과 네트워크에서 허용하면 다른 PC에서도 접근할 수 있다.

- (나) 🔍 `내주소` 로 접속했을 때 `closed-web-8081` 과 `open-web-8082` 의 결과(응답 번호)를 각각 적어 주세요.
  - 쓸 내용: ① closed-web-8081 의 응답 번호 ② open-web-8082 의 응답 번호
  - 답:
      - `closed-web-8081`: `000` — 내 PC의 IP 주소(`192.168.200.48`)로 접속했을 때 HTTP 응답을 받지 못했다.
      - `open-web-8082`: `200` — 같은 IP 주소로 접속했을 때 정상적으로 응답했다.

- (다) 🔍 `closed-web-8081` 은 `127.0.0.1` 로 접속하면 열려 있는데 `내주소` 로는 거부되는 이유는 무엇인가요? 다른 PC가 접속하는 경우와 어떻게 같은가요?
  - 쓸 내용: ① 127.0.0.1 로는 열리는 이유 ② 내주소로는 거부되는 이유 ③ 다른 PC가 접속하는 경우와 같은 점
  - 답:
      `closed-web-8081`은 `127.0.0.1`로 포트가 연결되어 있어 내 PC 내부에서만 접속할 수 있다. 따라서 `127.0.0.1:8081`로 접속하면 `200`이 나오지만, 내 PC의 네트워크 IP인 `192.168.200.48:8081`로 접속하면 `000`이 나온다. 다른 PC에서도 내 PC의 네트워크 IP로 접속해야 하므로 동일하게 접근이 거부된다.

- (라) 🔍 사내 PC에서 접속되면 안 되는 관리용 서버를 켠다면 `-p` 를 어떻게 쓰고, 이것이 4일 차의 어떤 원칙과 같은가요?
  - 쓸 내용: ① -p 에 쓸 형태 ② 같은 생각을 말하는 4일 차 원칙
  - 답:
      `-p 127.0.0.1:8081:80`으로 설정하여 내 PC 내부에서만 접근할 수 있도록 한다.

        이는 4일 차에 배운 방화벽의 허용 목록 원칙과 같다. 필요한 접근만 허용하고 나머지 접근은 차단하여 서버의 불필요한 노출을 방지한다.

- (마) 🔍 `docker inspect` 결과에서 두 서버의 `HostIp` 는 각각 무엇이고, `PORTS` 열의 어느 표시와 같은 뜻인가요?
  - 쓸 내용: ① closed-web-8081 의 HostIp ② open-web-8082 의 HostIp ③ 각각 `PORTS` 열의 어느 표시와 같은 뜻인지
  - 답:
      - `closed-web-8081`: `HostIp`는 `"127.0.0.1"`이며, `PORTS` 열의 `127.0.0.1:8081->80/tcp`와 같은 뜻이다. 내 PC 내부에서만 접근할 수 있다.

      - `open-web-8082`: `HostIp`는 `""`(빈 값)이며, `PORTS` 열의 `0.0.0.0:8082->80/tcp`와 같은 뜻이다. 특정 IP로 제한하지 않아 모든 네트워크 주소에서 접속을 받을 수 있다.

- (바) 🔍 `open-web-8082` 의 비밀번호가 `docker exec` 로 그대로 읽혔습니다. 왜 문제이고, 비밀번호를 환경변수에 넣을 때 어떻게 다뤄야 하나요?
  - 쓸 내용: ① 읽힌 값 ② 왜 문제인지 ③ 다룰 때 지킬 것 두 가지 이상
  - 답:
      `docker exec`로 환경변수를 확인했을 때 `DB_PASSWORD=dev-pass-1234`가 평문으로 출력되었다.

      이는 컨테이너의 환경변수를 읽을 권한이 있는 사람이 비밀번호를 그대로 확인할 수 있어 보안상 위험하다.

      따라서 비밀번호를 코드나 Docker 이미지에 직접 저장하지 않고, `.env` 파일도 GitHub에 올리지 않아야 한다. 필요한 컨테이너에만 전달하고, 실제 운영 환경에서는 Docker Secrets나 별도의 비밀 관리 서비스를 이용해야 한다.


- (사) 🔍 `whoami` 결과는 무엇이고, 이 서버가 침해되면 왜 위험이 커지나요? 6일 차 최소권한과 어떻게 이어지나요?
  - 쓸 내용: ① whoami 결과 ② 위험이 커지는 이유 ③ 최소권한과 이어지는 점
  - 답:
      `docker exec open-web-8082 whoami` 실행 결과는 `root`였다.

      `root`는 Linux의 최고 관리자 권한을 가진 사용자이므로, 서버가 침해되면 공격자가 컨테이너 내부의 파일, 환경변수, 설정 등을 변경하거나 중요한 정보를 탈취할 위험이 커진다.

      이는 6일 차에 배운 최소권한 원칙과 연결된다. 보안 위험을 줄이기 위해 프로그램에는 실행에 필요한 최소한의 권한만 부여하고, 가능하면 일반 사용자 권한으로 실행해야 한다.
